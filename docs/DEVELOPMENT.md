# Разработка «Напарника»

Общие технические заметки для Codex, Claude Code и разработчиков. Правила работы, команды, карта файлов и выпуск — в [AGENTS.md](../AGENTS.md), пользовательские возможности — в [README.md](../README.md).

Перед изменением механизма прочитай соответствующий раздел и проверь актуальный код. Приведённые замеры живой модели и API — исторические наблюдения, перенесённые из прежнего локального `CLAUDE.md`; они объясняют решения, но не подтверждают поведение текущей версии сервиса. Новые подтверждённые решения сохраняй здесь рядом с соответствующим механизмом.

## TypeScript и окружение

Версию компилятора проекта определяет `package-lock.json`; встроенный в VS Code компилятор может отличаться. В `tsconfig.json` явно указано `"types": ["node"]`: это сохраняет подключение Node-типов и в TypeScript 6. При ошибках только в редакторе сравни выбранный TypeScript с проектным. Не добавляй второй компилятор в зависимости ради обычной проверки.

## Архитектура

**Слои:** `src/api/` — сеть, чистый TS без `vscode` (тестируется на мок-сервере); `src/agent/` — работа с проектом; `src/chatViewProvider.ts` — оркестрация и webview; `media/chat.js` — UI в webview (обычный JS, без сборки, общается только через `postMessage`).

**API 1С:Напарник** (`src/api/client.ts`, `sseParser.ts`):
- `POST /chat_api/v1/conversations/` → `uuid` дискуссии; `POST …/{id}/messages` → SSE-поток.
- Тело сообщения: `content: { content: { instruction } }` — объект, не массив (иначе 422).
- Контекст между сообщениями — через `parent_uuid` = uuid последнего ответа ассистента; без него модель «забывает» чат.
- Серверные `tool_calls` подтверждаются следующим сообщением `role: "tool"` со `status: "accepted"` и `content: null` (иначе 422). Разрешены `mcp__knowledge-hub__*`, `mcp__syntax-checker__*`, `mcp__web__*` и `TodoWrite` (план задач модели — сервер выполняет его без EDT, а отказы от него подряд упирались в лимит раундов `MAX_TOOL_ROUNDS`); инструменты 1С:EDT (`WriteSystemFile`, `GetObject_in_Project`…) без сессии EDT падают — их отклоняем `status: "rejected"` с подсказкой (в чате — шаг «⛔ Недоступно вне 1С:EDT»). Вызовы без `id` — мусор сервера, ответ считается текстом.
- В одном SSE-потоке после ACK сначала идёт результат инструмента (`role: "tool"`, `finished: true`), потом ответ ассистента — события `tool` парсер пропускает. Поток читается до конца: сервер может сам отклонить вызов несуществующего инструмента («'Search_ITS' is unknown tool») и продолжить новым ответом — итог последний. Формат событий (сверено на 136 потоках): `{uuid, role, content: {content, tool_calls, reasoning_content}, content_delta, finished}`, строки `: heartbeat`; OpenAI-формата, `[DONE]` и JSON-обёрток результата нет.
- Зацикливание на инструментах (`TodoWrite` по кругу — сервер отвечает «continue to use the todo list», `Task`/`ReadSystemFile` после отказов, повтор того же вызова): после `MAX_IDLE_TOOL_ROUNDS` бесполезных раундов `sendMessage` пишет от пользователя `continueHint` (сервер принимает user-сообщение в ответ на неотвеченные tool_calls), затем задаёт вопрос заново от прежнего `parentUuid`. Не помогло и это — ответ `stalled` (вызовы не подтверждаются, текст `STALLED_TEXT`), а не ошибка лимита раундов: `runAgentLoop` шлёт `checkDone` или `AGENT_CONTINUE_HINT`, `/compact` считает пересказ несостоявшимся (живой API, `/init`: `ReadSystemFile` несозданного NAPARNIK.md 20+ раз, 1 из 9 прогонов падал). Отвечать на повторный эмулируемый вызов подсказкой «уже выполнено, дальше только @-команды» вместо чтения — хуже (5/6 → 3/6): модель отвечала намерением «Нужно использовать @-команды. Начну с…» без команд. `ReadSystemFile`/`ReadResource`/`WriteSystemFile` в агентном режиме выполняются как `@read_file`/`@create_file` (`emulatedCommand`; `ReadResource` модель зовёт с путями `memory://CLAUDE.md`, `attachment://…`), результат уходит в `rejected`-ответе инструменту.
- Ветвление: сообщение можно отправить от любого прежнего ответа ассистента — поэтому после ошибки или «Стоп» чат откатывает `lastAssistantUuid`/`agentPrimed` к состоянию до запроса, а не сбрасывает дискуссию.
- Таймаут — по паузе в событиях (`IdleTimeout` продлевают только строки `data:`, не `: heartbeat` — завис с heartbeat, и `/init` висел 26+ минут), сервер может молчать ~160 с перед ответом. Таймаут после подтверждения инструмента (`toolsAcked`) — не ошибка, а `askToContinue`.
- Честный `User-Agent: naparnik-1c-vscode/<версия> (unofficial)`, без подделки заголовков веб-чата.
- Пределы (замер на живом API): одно сообщение до ~300 тыс. символов модель дочитывает до конца, на 600 тыс. — «Не удалось сформировать ответ»; контекст дискуссии общий (`max_context_length` = 262144 токена). Свои лимиты на объём выбирать с запасом.
- Заполненность контекста — в `details` финального события ответа: `usage.total_tokens` и `max_context_length` (`SseParser` → `ChatAnswer.usage`). Пустая дискуссия — 6–9 тыс. токенов (системный промпт сервера); код 1С ≈ 2,3 символа на токен, русский текст ≈ 4. **При переполнении ошибки нет**: сервер молча выбрасывает старые сообщения ветки, `total_tokens` следующего ответа становится меньше прежнего.

**Агентный режим** (`src/agent/protocol.ts`, `agentLoop.ts`, `workspaceTools.ts`): API не принимает клиентские инструменты, поэтому команды описываются модели текстом в первом сообщении (`buildAgentPrompt`), а цикл `runAgentLoop` (без `vscode`, тестируется на моках) ищет их в ответе (`parseCommands`), выполняет и отправляет «Результаты команд», пока не придёт ответ без команд. На последнем шаге лимита (`MAX_AGENT_STEPS`, для `/init`/`/make-rules` — 25) модель получает `FINISH_HINT` «заверши по собранному»; ответ-намерение без команд (`looksLikeUnfinishedIntent`: «читаю…», «нужно добавить…», короткий ответ на «:») и `checkDone(executed, answerText)` (для `/init` — создан ли NAPARNIK.md) дают до двух напоминаний продолжить. В регулярках по русскому тексту не использовать `\b` — в JS он не работает с кириллицей.
- Синтаксис — строки `@list_dir папка | глубина`, `@read_file`, `@search текст | маска`, блоки `@edit_file путь … SEARCH/REPLACE … @end` и `@create_file путь … @end`, `@move_file откуда | куда`, `@copy_file`, `@delete_file` (подтверждаются карточкой `EditPreview.confirmOperation`, без diff; после переноса расширение само ищет старый путь — подсказка «найди через @search» стоила модели лишних раундов). **Не XML**: XML-теги сервер принимает за свои tool_calls и обрезает ответ. XML-разбор оставлен только как запасной.
- После применённой правки `.bsl` цикл добавляет к результатам изменённые процедуры (`changedCode`) и просит модель вызвать серверный `mcp__syntax-checker__validate` (`{code, extended}`) — сами вызвать его не можем, код в инструмент передаёт модель. Без «вызови как поиск по ИТС, не пиши @validate» модель в половине ответов писала вызов текстом; ответ «@Имя…»/«mcp__…» без команд (`looksLikeTextToolCall`) — напоминание с повтором запроса. Без «code — ровно как есть, исправляй через @edit_file» модель проверяла свою исправленную в уме версию и не применяла правку.
- @-упоминания в вопросе (`agent/mentions.ts`) прикладывают файлы и папки к сообщению в `chatViewProvider.send`; папки в индексе путей — с «/» на конце (`withFolders`), раскрываются `folderFiles` (описания и верхние уровни первыми); файлы папки — только целиком (`pickFolderFiles`: обрезанный Form.xml вытеснял модули форм), в остаток лимита после явно упомянутых файлов, читается до `MAX_FOLDER_FILES_READ`; в папке бывают десятки тысяч файлов — проверки через `Set`, не `includes`; автодополнение — `mentionQuery`/`mentionResults` между webview и расширением; выбранный в подсказке путь убирается из текста и становится чипом (`addAttachment`), набранный вручную `@путь` разбирается при отправке. Блок файлов начинается с их перечня — без него модель после длинных файлов теряла последний; не поместившиеся — отдельным блоком с числом и «содержимого нет» (без этого на папке в 1900 файлов модель называла 3 или 18 файлов вместо 68: 2/6 → 6/6). Файлы и папки из проводника и с вкладки (`naparnik.addToContext` в `explorer/context` и `editor/title/context`, VS Code передаёт `(uri, uris)` — все выделенные), перетащенные в webview (`dropUris`: `application/vnd.code.uri-list`/`text/uri-list`/`ResourceURLs`/`CodeEditors` — перетаскивание вручную в VS Code не проверено) и фрагменты (`naparnik.addSelectionToContext`, ключ `путь#L120-180`, строки читаются при отправке) копятся в `SavedChat.attachments` — у каждого чата свои, сохраняются без смены `updatedAt` (чипы, `removeAttachment`). Папка не поместилась (`overflowFolders`) — модель дочитывает её сама: подсказка `overflowReadHint` после блока файлов; без доступа к проекту — `FolderReadTools` (только `@read_file`/`@list_dir`/`@search` внутри этих папок, без агентного промпта; без подсказки с синтаксисом команд модель их не знает), с доступом — короткая подсказка, команды ей уже известны. `AgentTools.readOnly`: цикл не напоминает формат правки (иначе модель писала её снова и сырая `@edit_file` становилась ответом — 4/6 → 6/6), а шлёт `READ_ONLY_HINT`; общие напоминания (`CONTINUE_HINT`, `TEXT_TOOL_CALL_HINT`) перечисляют команды изменения и толкали к правке — в этом режиме свои (`READ_ONLY_*`); повторная правка после отказа — сразу `READ_ONLY_ANSWER` вместо сырой команды; шаги изменения — «⛔ Недоступно без доступа к проекту». В подсказке дочитывания — «точного пути не знаешь — @search имя_файла»: список не приложенных обрезан, и модель угадывала соседний файл. Маска поиска без `*?.` — имя папки (модель писала `@search текст | tests`). Объём на чипах считает тот же `gatherContext`, что и отправка (`attachmentStats`, устаревший расчёт отбрасывается по `statsSeq`) и уходят в `resolveMentions` с каждым вопросом пользователя — после отправки чипы остаются, неизменённый блок файлов повторно не шлётся (хеш `lastAttachments`, как у контекста редактора). Прямо перед вопросом — `formatSelection`: что выбрано (папки отдельно от файлов), иначе на «какие папки в контексте» модель отвечала по дереву проекта или перечисляла подпапки (живой API: 0/6 → 6/6); выделение в проводнике API не сообщает — только через команду.
- Парсер терпит ошибки модели: `@end` в той же строке («@read_file a.md @end» — отбрасывается), забытый `@end` (блок закрывает следующая команда — но строка `@read_file` внутри текста файла не считается командой, если ниже есть `@end`), содержимое файла в обёртке SEARCH/REPLACE, блок правки, закрытый «=======» вместо «>>>>>>> REPLACE» или не закрытый, правка без `@edit_file` (один раз напоминаем формат).
- Каждое изменение файла — только после подтверждения: `EditPreview` открывает diff через виртуальную схему `naparnik-proposed` и ждёт решения из карточки в чате или кнопок/клавиш в diff. Правка привязана к id чата (`owner`). «Стоп» и закрытие вкладки — отказ. Перед записью файл перечитывается: изменился во время просмотра — правка не применяется.
- Карта проекта (`tree()`): небольшой проект — целиком (модули форм 1С лежат на 6–7 уровнях); большой — самое глубокое дерево до 4 уровней, которое помещается в 250 строк, с «… ещё N» в больших папках (иначе первая большая папка съедает весь бюджет). Поиск (`collectFiles`) обходит папки сам и не заходит в игнорируемые — `findFiles` с лимитом отдал бы его игнорируемым зависимостям. Скрывается только то, что игнорирует git: `.gitignore` во всех папках (каждый относительно своей, `agent/gitignore.ts`) и папка `.git`; скрытое не видно в карте и поиске, но читается явно. Не добавлять в код списки папок, расширений или «секретных» файлов — расширение работает с любым проектом и не решает за него, что скрывать.
- `WorkspaceTools`: пути только внутри корня (с проверкой `realpath` — симлинки наружу запрещены), BOM и CRLF файлов 1С сохраняются, открытые документы читаются/пишутся через редактор.
- Первое сообщение чата с доступом к проекту получает дерево проекта, найденную документацию и инструкции ИИ-инструментов (`PROJECT_DOC_FILES/DIRS` в `slashCommands.ts`; ищутся в корне и в папках первого уровня — рабочая папка может содержать несколько проектов), `NAPARNIK.md` и правила из `.rules/` (приоритетнее остального). Если документации нет, модели прямо говорится «не ищи».

**Git** (`agent/gitTools.ts`, без `vscode`; репозиторий — `findGitRepository` в `workspaceTools.ts`): под капотом, без своего интерфейса и слэш-команд — пользователь просит словами, модель пишет `@git_status`, `@git_diff [файл]`, `@git_log [N]`, `@git_branch` (выполняются сразу), `@git_create_branch`, `@git_checkout`, `@git_commit` … `@end`, `@git_pull`, `@git_push` (карточка `EditPreview.confirmGit` — та же, что у переноса/удаления). Через API встроенного `vscode.git`, не терминал; в промпте раздел git — только если репозиторий найден. Опасного (reset, rebase, force, удаление веток, настройки) нет вовсе; checkout — только на существующую ветку. Ловушки API: `diffWithHEAD(path)` — это `git diff -- path` (рабочая папка против индекса), staged — `diffIndexWithHEAD`; сразу после открытия репозитория `state.HEAD` пуст — `run` сначала вызывает `repo.status()`; коммит с `postCommitCommand: null`, иначе настройка `git.postCommitCommand` сделает push; в коммит — staged, если есть, иначе всё (`git add`). Без «посмотри @git_log 5, пиши в стиле проекта» модель писала сообщения без `fix:`, хотя в журнале они с ним (живой API: 0/6 → 6/6); пример блока коммита — заглушка `СООБЩЕНИЕ`, иначе модель копировала текст примера в сообщение. Git не работает в недоверенной папке (`untrustedWorkspaces: false` у `vscode.git`).
Промптом модель от лишних git-действий не удержать (на «запушь» коммитила 6/6, после отказа предлагала тот же коммит до 10 раз, после отклонённого push крутила pull/push с `--rebase`/`--force-with-lease`, на «перейди на release» создавала ветку) — защита в коде: (1) `requestedByUser` — git-действие выполняется, только если о нём есть глагол в вопросе пользователя или в предыдущем ответе Напарника («закоммитить?» → «да»); «коммиты» — не просьба о коммите; (2) `GitTools.blocked` — отказ пользователя или ошибка git блокирует повтор той же команды до конца запроса, без карточки; (3) в `runAgentLoop` git-действие в одном ответе с непросмотренным чтением git откладывается (`GIT_DEFERRED_HINT`): коммит писался до diff («initial commit»), pull добавлялся до статуса; (4) тексты ошибок без подсказки обхода («Сначала нужен @git_pull» и «создать — @git_create_branch» сами толкали к ним). Флаги CLI: `-m` у коммита и `-b` у checkout понимаются, `--force`/`--rebase` у push/pull — отказ; `@git push` через пробел — как `@git_push`; несуществующая `@git reset…` — `GIT_UNSUPPORTED_HINT`, если модель настаивает — `gitUnsupportedAnswer` вместо сырой строки. Ответ-вопрос или предложение («Хотите…?», «если нужно — сделаю») `looksLikeUnfinishedIntent` не подталкивает: напоминание заставляло модель делать предложенное (после pull она заново применила diff к файлам). Проверка на живом проекте — на клоне во временной папке с bare-remote: настоящий remote может содержать чужие или личные данные, а pull/log/diff отправят их в сервис.

**`/import`** (`agent/importSources.ts`, без `vscode`): сканирует инструкции других ИИ-инструментов (CLAUDE.md, AGENTS.md, GEMINI.md, правила Cursor/Copilot/Windsurf, пользовательские `~/.claude/CLAUDE.md` и т. п. — только с согласия) и отдаёт модели их содержимое вместе с текущими `.rules/` одним сообщением, чтобы она записала правила без лишних чтений. Хеши перенесённого — в `workspaceState`, повторный запуск берёт только новое. `importDone` различает отказ сервера и осознанное «переносить нечего» (строка «Противоречия: …»): давление «запиши» после отказа заставляло модель выдумывать правила. Сервер иногда отвечает «внешнее API предназначено для 1С:EDT» — почти только когда в переносимых файлах речь о других ассистентах (Claude, MCP, субагенты); в `/init` и обычных вопросах такого не наблюдалось.

**`/compact`** (`agent/compact.ts`, без `vscode`; оркестрация — `compact()` в `chatViewProvider.ts`): пересказ просится в той же дискуссии от `lastAssistantUuid` (модель помнит прочитанные файлы) — `compactPrompt` с перечнем сообщений пользователя (`userMessages`): без него Qwen терял сказанное в первом сообщении (оно тонет в агентном промпте) и записывал в «указания» служебные инструкции про @-команды (живой API: 1/4 → 6/6, ещё помог процедурный пункт «пройди по каждому моему сообщению… названия, номера — дословно»). Не вышло (ошибка, отказ, дискуссии нет) или `contextTruncated` (начало уже выброшено) — по записи `buildTranscript` в новой дискуссии. Запись и перечень — с последнего пересказа. После сжатия сбрасываются дискуссия, `agentPrimed`, хеши контекста, пересказ ждёт в `compactSummary` и уходит `summaryBlock` перед следующим вопросом (лишнего запроса нет; при доступе к проекту агентный промпт пришлётся заново сам); в истории — запись `role: 'compact'`, файлов нет. Автосжатие (`naparnik.autoCompact`, по умолчанию вкл.) — в `send` до отправки по прогнозу `needsAutoCompact` (85%); подсказка — после ответа на 70%; уменьшение `usage` — предупреждение о выброшенном начале. Внутри агентного цикла переполнение не предотвращается — только замечается после ответа.

**Клиент:** HTTP 429 (лимит общий на все дискуссии токена) показывается понятным текстом; пустой ответ сервера — один раз напоминание продолжить от последнего `assistantUuid` (`askToContinue` с `continueHint`), а не ошибка.

**Чат** (`chatViewProvider.ts`): у каждого чата свой `RunningRequest` — запросы в разных чатах идут параллельно, сообщения в webview уходят только для видимого чата (`postIfVisible`). История — `globalState` (`chatHistory.ts`), доступ к проекту — `workspaceState`, токен — `SecretStorage`. Слэш-команды разбираются в расширении (`slashCommands.ts`) и работают во время ответа; `/init` и `/make-rules` отправляют модели развёрнутые инструкции вместо видимого текста. Контекст редактора (`editorContextTracker.ts` + `agent/editorContext.ts`) прикладывает открытый файл/выделение и ошибки VS Code к каждому вопросу; тот же неизменённый файл повторно не шлётся (хеш в истории). Открытый файл, чей текст уже ушёл среди приложенного (чип, папка, @-упоминание — `shownFiles` из `resolveMentions`), шлётся отсылкой без текста (`formatEditorContext(…, textAttached)`), а его чип прячется: без отсылки модель не знала, какой файл открыт, и на «в этом файле» отвечала про соседний; выделение дублем не считается. Под полем ввода — шкала `contextUsage` и ветка (`watchGitBranch` → `repo.state.onDidChange`).

## Проверка изменений

- Логика без `vscode` — unit-тесты в `src/test/`. Код с `vscode` (`WorkspaceTools`, `EditPreview`, трекер редактора) unit-тестами не покрыт — проверять в настоящем VS Code. `@vscode/test-electron` не нужен: установленный VS Code запускает тестовый скрипт (модуль с `exports.run`) в extension host — `"/Applications/Visual Studio Code.app/Contents/MacOS/Code" --disable-extensions --user-data-dir=<короче 103 символов> --extensions-dir=<tmp> --extensionDevelopmentPath=<проект> --extensionTestsPath=<скрипт> <временная папка проекта>`; окно закрывается само, когда `run()` завершится. Удаление в тестах уходит в корзину ОС. `--disable-extensions` выключает и встроенные расширения (нет `vscode.git`) — для git запускать без него (каталог расширений и так временный) и с `{"security.workspace.trust.enabled": false}` в `<user-data-dir>/User/settings.json`, иначе папка недоверенная и Git выключен.
- Поведение модели проверять на живом API (токен — только в переменной окружения, `NAPARNIK_API_TOKEN` для штатного набора, не в файлах): модель часто нарушает формат команд, и тесты на моках этого не ловят. Харнесс — настоящий `runAgentLoop` + `buildAgentPrompt` с инструментами в памяти, результаты команд — теми же строками, что у `WorkspaceTools` (от них зависит, например, проверка синтаксиса).
- Живой набор — `npm run test:live` (`src/test-live/`, не входит в `npm test` и `.vsix`): весь трафик идёт через локальный прокси (`proxy.ts`) — лимит 10 запросов/мин и 150 на прогон, сбои 429/5xx/обрыв/пауза/разрезанный UTF-8 по URL `/__f/<id>/<спецификация>`; группы `api`/`faults` — `NaparnikClient` в Node, остальные — настоящий `ChatViewProvider` в установленном VS Code на APFS-копии проекта в `/tmp/naparnik-test` без git remote. Аргументы `--group=…`, `--only=…`, `--project=…`, `--keep`; метрики — `test-results/live-*.json`. g5-autotests — не 1С (Playwright/TS), модули `.bsl` для сценариев набор кладёт в копию сам.
- Ответы модели шумные: выводы — по 6+ прогонам на сценарий, при подозрении на регрессию — A/B с прежним промптом (так нашлось, что новые команды в `buildAgentPrompt` подтолкнули `/import` к дублям). Не больше 2 дискуссий параллельно: при 4 сервер быстро отвечает 429 на ~2 минуты.
