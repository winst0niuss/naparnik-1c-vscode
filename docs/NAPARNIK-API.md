# API 1С:Напарник: интеграция в веб-приложение

Описание по реализации расширения «Напарник» 1.0.5. API `https://code.1c.ai` недокументированный: ниже — используемый нами протокол, его стабильность сервисом не гарантируется.

## Схема интеграции

Рекомендуемая схема: **браузер → ваш бэкенд → API Напарника**. Бэкенд хранит токен, отправляет POST-запросы, обрабатывает серверные инструменты и передаёт текст ответа в браузер потоком. Прямые запросы из браузера и CORS в нашем проекте не проверялись.

Для каждого чата храните `conversationId` и UUID последнего успешного ответа ассистента — `parentUuid`. Привязывайте их к пользователю приложения.

## 1. Авторизация и создание чата

Нужен API-токен из личного кабинета `code.1c.ai`. У нас по умолчанию он передаётся **без `Bearer`**:

```http
Authorization: <API_TOKEN>
Content-Type: application/json; charset=utf-8
User-Agent: <имя-вашего-приложения>/<версия> (unofficial)
```

Создание дискуссии: `POST /chat_api/v1/conversations/`. Дополнительные заголовки нашего клиента: `Accept: */*`, пустой `Session-Id`, `Accept-Language: ru-ru,en-us;q=0.8,en;q=0.7`.

```json
{
  "tool_name": "custom",
  "skill_name": "custom",
  "ui_language": "russian",
  "script_language": "ru",
  "is_chat": true
}
```

Ответ содержит `uuid` — сохраните его как `conversationId`. `skill_name: "custom"` позволяет использовать поиск и документацию; `"raw"` — режим ответа без этих возможностей.

## 2. Отправка сообщения

`POST /chat_api/v1/conversations/{conversationId}/messages`, заголовок `Accept: text/event-stream`, остальные заголовки авторизации те же.

```json
{
  "parent_uuid": null,
  "role": "user",
  "content": {
    "content": {
      "instruction": "Как объявить экспортную процедуру в 1С?"
    }
  }
}
```

В первом сообщении `parent_uuid: null`, в последующих — UUID предыдущего ответа ассистента. Без этой связи модель не видит нужную ветку истории. `content` пользовательского сообщения — **объект**, массив вызывает HTTP 422.

## 3. Чтение SSE

Ответ на POST — поток строк `data: <JSON>`, например:

```text
data: {"uuid":"<assistant_uuid>","role":"assistant","content_delta":{"content":"Ответ"},"finished":false}

data: {"uuid":"<assistant_uuid>","role":"assistant","content":{"content":"Ответ"},"finished":true}
```

- Декодируйте UTF-8 потоково и собирайте строки: сетевой chunk может закончиться посреди символа или JSON.
- Накапливайте `content_delta`: это строка либо объект с полем `content`. Непустой финальный `content.content` или `content.text` заменяет накопленный текст; пустой его не стирает.
- Пропускайте события `role: "user"`, `role: "tool"` и комментарии `: heartbeat`. Дельты могут иметь `role: null` или не содержать `role` — их обрабатываем. Поле `reasoning_content` и блоки `<think>`/`<thinking>` не показываем пользователю.
- Читайте поток **до закрытия**, даже после `finished: true`: в одном потоке бывают несколько ответов, итоговым считается последний. UUID берём из событий `role: "assistant"`.
- Формата `choices/delta` и маркера `[DONE]` здесь нет. Поток, закрывшийся посреди незавершённого ответа ассистента, считаем обрывом.

## 4. Серверные инструменты

Вместо готового ответа ассистент может вернуть `tool_calls` внутри `content` или `content_delta` — массив вызовов с `id`, `function.name` и `function.arguments` (аргументы — JSON в строке). После чтения потока отправьте на **тот же endpoint сообщений** подтверждение:

```json
{
  "parent_uuid": "<uuid_ответа_с_tool_calls>",
  "role": "tool",
  "content": [
    {
      "tool_call_id": "<id_вызова>",
      "status": "accepted",
      "content": null
    }
  ]
}
```

Сервер сам выполняет подтверждённые инструменты и возвращает новый SSE-поток. Повторяйте цикл до текстового ответа без вызовов. Для `role: "tool"` поле `content` — **массив**, по элементу на каждый вызов с `id`.

У нас разрешены `mcp__knowledge-hub__*`, `mcp__syntax-checker__*`, `mcp__web__*` и `TodoWrite`. У разрешённого вызова обязательно `status: "accepted"`, `content: null`. Для подтверждения также нужен UUID ответа ассистента; если его нет, клиент возвращает ошибку.

Остальные инструменты без локальной реализации отклоняем. Например, `WriteSystemFile` и `GetObject_in_Project` требуют сессии проекта 1С:EDT. Отвечаем `status: "rejected"`, а в `content` передаём строку: «Инструмент недоступен: работа идёт не из 1С:EDT, сессии проекта нет. Ответь без него». Вызовы без `id` не подтверждаем.

## 5. Ошибки, лимиты и состояние

Числа ниже — настройки и защитные пороги нашего клиента, а не квоты API.

| Ситуация | Что делаем у нас |
| --- | --- |
| HTTP 401/403 | Ошибка авторизации, без автоматического повтора |
| HTTP 422 | Проверяем тело запроса и связь с `tool_calls`; при `No tool calls found` пробуем попросить продолжить, если известен UUID предыдущего ответа и доступна попытка восстановления |
| HTTP 429, 500, 502, 503, 504 или сбой сети до получения ответа | До 4 попыток; `Retry-After` либо задержки 1, 2, 4 с с разбросом. При `Retry-After` больше 30 с возвращаем ошибку пользователю |
| Обрыв уже начавшегося SSE | Сохраняем частичный текст, отмечаем ответ незавершённым; автоматически запрос не повторяем |
| Нет событий SSE | Таймаут по бездействию, по умолчанию 300 с; продлевается только строками `data:`, heartbeat его не сбрасывает |
| Пустой ответ, повторяющиеся инструменты или таймаут после подтверждения инструментов | При наличии UUID просим ответить текстом; затем можем повторить исходный вопрос от прежнего `parentUuid`. До 2 попыток восстановления; порог защиты — 25 раундов или 3 бесполезных раунда подряд. Если инструменты продолжают зацикливаться, возвращаем `stalled: true` |

Обновляйте `parentUuid` после успешного ответа. При отмене, сетевой ошибке или HTTP 5xx сохраняем прежнюю ветку. Если HTTP 4xx, кроме 401/403/429, дошёл до слоя чата, сбрасываем `conversationId` и `parentUuid`: следующий вопрос создаст новую дискуссию. Лимит частоты общий для дискуссий одного токена.

Заполненность контекста, если сервис её передал, берём из финального события: `details.usage.total_tokens` и `details.max_context_length`. При переполнении сервис может молча отбросить начало истории. Сжатие реализовано в расширении и включено по умолчанию: если прогноз с учётом нового сообщения превышает 85%, просим модель пересказать разговор, затем передаём пересказ вместе со следующим вопросом в новую дискуссию. При ошибке пересказа старую дискуссию сохраняем. При переносе только API-клиента эту логику нужно добавить отдельно.
