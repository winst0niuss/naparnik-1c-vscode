# Roadmap

Планы развития расширения «Напарник». Порядок — примерный приоритет.

## 1. Слэш-команды в чате (как в Claude Code)

Ввод `/` в поле чата открывает список команд с подсказками; команда выполняется в расширении и не отправляется Напарнику как вопрос (кроме `/init`).

| Команда | Что делает |
|---------|-----------|
| `/init` | Напарник изучает проект и создаёт файл `NAPARNIK.md` с описанием: назначение, структура, ключевые модули, соглашения. Файл автоматически добавляется в первое сообщение каждого нового чата с доступом к проекту — модели не нужно заново исследовать проект. Создание — через обычный diff с подтверждением. |
| `/clear` | Начать новый чат с чистым контекстом (то же, что кнопка «+»). Текущий чат остаётся в истории. |
| `/exit` | Остановить текущий ответ и закрыть панель Напарника. |
| `/help` | Список команд с описанием. |
| `/history` | Открыть историю чатов. |
| `/project` | Включить или выключить доступ к проекту. |
| `/token` | Задать API-токен. |
| `/stop` | Остановить текущий ответ (то же, что кнопка «Стоп»). |

Детали:
- Автодополнение: список фильтруется по введённому тексту, выбор стрелками и Enter/Tab.
- Неизвестная команда — подсказка «нет такой команды, см. /help», запрос не уходит.
- `NAPARNIK.md` — обычный файл в корне проекта: его можно править вручную и хранить в git, чтобы вся команда работала с одним описанием.

## 2. Скорость и понятность долгих ответов

Замер на запросе «создай файл со структурой проекта»: сервер 1С:Напарник ~160 с ничего не присылает, затем ~70 с передаёт текст файла. Пользователь всё это время видит только «Напарник думает».

- Пока модель пишет содержимое файла (команда `@create_file` / `@edit_file` ещё не закончена), показывать «✍️ Пишет PROJECT_STRUCTURE.md… 1 580 символов» вместо «думает».
- Секундомер — на каждый этап отдельно («думает», «ждёт решения», «пишет файл»), а не общий с начала вопроса.
- Таймаут считать по паузе между данными, а не на весь ответ: длинный, но идущий ответ не должен обрываться.
- `/init` (см. выше) сократит первый ответ: вместо полного дерева — готовое описание проекта.

## 3. Работа с git

Напарник понимает состояние репозитория и выполняет базовые операции. Работает через встроенное расширение Git в VS Code (`vscode.git`), а не через произвольные команды терминала — так набор действий ограничен и предсказуем.

Любое действие с git — даже просмотр статуса или diff — Напарник выполняет только после разрешения пользователя: в чате появляется карточка с командой и кнопками «Разрешить» / «Отклонить».

Новые команды для модели (в том же `@`-протоколе):

| Команда | Что делает | Подтверждение |
|---------|-----------|---------------|
| `@git_status` | Текущая ветка, изменённые / новые / удалённые файлы, отставание от remote | карточка в чате |
| `@git_diff [файл]` | Diff незакоммиченных изменений (всех или одного файла) | карточка в чате |
| `@git_log [N]` | Последние N коммитов | карточка в чате |
| `@git_branch` | Список веток | карточка в чате |
| `@git_create_branch имя` | Создать ветку и переключиться на неё | карточка в чате |
| `@git_checkout ветка` | Переключиться на существующую ветку | карточка в чате |
| `@git_commit` + сообщение | Закоммитить изменения (все или выбранные файлы) | карточка: сообщение коммита (можно отредактировать) и список файлов |
| `@git_pull` | Подтянуть изменения из remote | карточка в чате |
| `@git_push` | Отправить текущую ветку в remote | карточка: ветка и remote |

Слэш-команды для пользователя:
- `/commit` — Напарник смотрит diff и предлагает сообщение коммита (по умолчанию в формате conventional commits).
- `/review` — Напарник делает ревью незакоммиченных изменений.
- `/branch имя` — создать ветку.

Безопасность:
- Каждая git-операция — только после разрешения в чате; без ответа пользователя ничего не выполняется.
- Запрещено: `push --force`, `reset --hard`, переписывание истории, удаление веток, изменение настроек git и remote.
- Push в `main`/`master` — с отдельным предупреждением.
- Diff и список файлов отправляются в сервис 1С:Напарник — как и файлы проекта, только при включённом «Доступе к проекту».
- Конфликты при pull — не разрешать автоматически: показать список и предложить открыть их в редакторе.

## 4. Работа с проектом

- Учитывать `.gitignore` при поиске и построении дерева.
- Карточка правки показывается только в том чате, где её предложили.
- `@-упоминания` файлов в вопросе: `@ObjectModule.bsl` — файл прикладывается к сообщению без включения полного доступа к проекту.
- Проверка синтаксиса BSL после правки через инструмент сервиса `mcp__syntax-checker__validate`.
